## Deterministic duplicate-review progress

`season_milestone_progress_v1.py` compares immutable cross-club identity audits.
It never edits recipes or games. An absent candidate is **awaiting verification**,
not a confirmed fix. This is queue measurement, not historical completion,
within-club/photo coverage, or a fresh runtime/registry check.

The frozen R39 baseline and R39/R47 reports are in
`.local/milestone-progress-v1/duplicate-review-r39-r47-20261007-r1/`.
Baseline SHA256 (external pin):
`ee1168de790972b02af10c7f241a8335821b16ddcfc6c16f4b8355d8d8561050`.
R47 report SHA256:
`d4e9ab8d22bb179e53879d8381e634a305e25961a196e1e0f9269bfebaf63069`.
`reproducibility-proof.json` binds the inputs/code and identical repeat output.

After an existing repair audit finishes, create a new report using the same
baseline and the preceding report. Do not regenerate games to measure progress:

```sh
python3 scripts/season_milestone_progress_v1.py report \
  --baseline .local/milestone-progress-v1/duplicate-review-r39-r47-20261007-r1/baseline.json \
  --baseline-sha256 ee1168de790972b02af10c7f241a8335821b16ddcfc6c16f4b8355d8d8561050 \
  --audit PATH_TO_NEW_IMMUTABLE_AUDIT.json \
  --previous .local/milestone-progress-v1/duplicate-review-r39-r47-20261007-r1/r47.json \
  --previous-sha256 d4e9ab8d22bb179e53879d8381e634a305e25961a196e1e0f9269bfebaf63069 \
  --output PATH_TO_NEW_PROGRESS_REPORT.json
```

Every output is exclusive-create. All 26 seasons, declared counts, distinct
carriers, multi-club candidate membership and source/layer bindings are checked.
The full contract, baseline audit and measurement implementation are pinned;
changing rules/code requires an explicitly new baseline, not denominator drift.
Stable IDs use exact season + typed identity. Changed memberships are reported
separately. New discoveries stay outside the original denominator and persist
through the supplied report chain, even after disappearing.

Previous reports are recursively reproduced, not trusted status lists.
Returning candidates are flagged only across supplied checkpoints; missing
history means recurrence **not assessed**, not zero regressions. This cannot
detect omitted checkpoints or prove a historical repair merely from audit
disappearance. Verified-completion and proven-fix-regression fields deliberately
remain unavailable until an independent disposition adapter exists. No manual
`verified=true` shortcut is accepted. The v1 ancestry cap is 256 reports; rotation
needs an explicit evidence-preserving baseline change.

## Reusable season-authoring flow

Native clone identities are validated by the compiler and season QA. To apply
only the proven ID repair to existing releases, without rescraping or rebuilding
any editorial content:

```sh
python3 scripts/repair_registered_player_identities_v1.py all --register
```

This is idempotent for already-correct seasons. Every mismatch must match its
recipe's declared append donor; all other changes fail closed. Unchanged game
files are hardlinked, the new JUG file is atomically replaced, old releases are
retained and stale QA/runtime attestations are not inherited. Use
`./pm99-season prove YYYY-YY --worker NAME --execute --attest` for fresh evidence.
The crash controls and bounded repair are documented in
[`2004_05_SETUP_CRASH_REPAIR_2026-10-03.md`](../docs/2004_05_SETUP_CRASH_REPAIR_2026-10-03.md).

The reusable authoring flow has deliberately separate source and package
boundaries. A raw capture must never be renamed to a package simply because it
has enough player rows.

1. `season_recipe_v1.py` validates a data-only, hash-locked recipe: the
   verified-base descriptor, static mode-0/mode-1 carrier maps, dated source
   captures and small editorial overlay documents. It does not read a game
   tree or write a package/database.

   A buildable V1 recipe must declare dated squad, manager, opening-lineup and
   kit lanes. Its fixed historical policy is: select players who were at the
   club on its first league-fixture date and exclude later arrivals; use the
   published first-XI formation or a deterministic position-based inference;
   require the correct opening-date manager with no native fallback; preserve
   a continuing club's native name; require a target-season kit for continuing
   clubs; and preserve a native kit only when its carrier's historical club
   has exited. Native opening state has the same exited-carrier-only limit.
   Ratings may use the declared deterministic editorial model.
   Nationality, birth date, height, weight and shirt number are sourced where
   available. A missing secondary fact does not block V1: the package intake
   supplies a usable deterministic/nearby-season value or an explicit mode-1
   preserve request, and records a field-scoped `fact_fallbacks` row containing
   the method, exact value, reason and proof. Primary position remains required.
   Every player also receives a portrait declaration; when no suitable image is
   available, `native-no-photo` is the deliberate non-blocking result.

   ```bash
   python3 scripts/season_recipe_v1.py validate \
     --recipe <season-directory>/season-recipe.json
   python3 scripts/season_recipe_v1.py verify-inputs \
     --recipe <season-directory>/season-recipe.json
   ```

2. When a dated season has more than one complementary source capture,
   `season_source_bundle_v1.py` is the generic, data-only composition step.
   Its bundle manifest names every input and its SHA-256, the logical season
   label, the immutable carrier registry, and the old assignment it may
   safely rebind. It creates one canonical composed capture and a freshly
   hash-bound assignment ledger; it neither chooses a historic identity nor
   writes PM99.

   ```bash
   python3 scripts/season_source_bundle_v1.py build \
     --bundle <season-directory>/source-bundle.json
   python3 scripts/season_source_bundle_v1.py verify \
     --bundle <season-directory>/source-bundle.json
   ```

   Reprocess that explicit bundle through the batch coordinator with its
   declared derived assignment filename. The coordinator still refuses any
   unbundled competing captures.

   ```bash
   python3 scripts/season_source_intake_batch_v1.py \
     --seasons-root seasons --season <season-id> \
     --assignment-name foreign-carrier-assignment-composed.json --write
   ```

3. `season_source_intake_v1.py` makes a raw
   `pm99-season-source-intake-v1` from one dated squad capture, the immutable
   mode-1 registry and the carrier-assignment ledger. It retains every source
   row and every unresolved source fact, and records candidate/unassigned
   carriers as such. It has no reconciled people, PM99 player-slot bindings,
   ratings, managers, opening fixtures, kits, portraits, package or database
   output.

   ```bash
   python3 scripts/season_source_intake_v1.py build \
     --registry <season-directory>/fixed-carrier-registry.json \
     --source-capture <season-directory>/sources/footballsquads.json \
     --assignment <season-directory>/foreign-carrier-assignment.json \
     --intake-id <stable-source-intake-id> \
     --output <season-directory>/source-intake.json
   python3 scripts/season_source_intake_v1.py audit \
     --registry <season-directory>/fixed-carrier-registry.json \
     --source-capture <season-directory>/sources/footballsquads.json \
     --assignment <season-directory>/foreign-carrier-assignment.json \
     --intake <season-directory>/source-intake.json \
     --output <season-directory>/source-intake-audit.json
   ```

   Opening manager evidence is materialised independently from the cached
   first-league-match reports. The manager stage covers every squad-source
   club, emits explicit gaps, and accepts only canonical dated supplements
   carrying a source URL and snapshot SHA-256. It never substitutes a native
   or current manager.

   ```bash
   python3 scripts/materialise_opening_manager_ledger_v1.py \
     --source-capture <season-directory>/sources/footballsquads.json \
     --opening-lineups <local-source-root>/opening-lineup-source-v1.json \
     --supplement <season-directory>/sources/opening-manager-supplement-v1.json \
     --output <local-source-root>/opening-manager-ledger-v1.json \
     --strict
   ```

   `capture_opening_manager_history_supplements_v1.py` creates that dated,
   hash-bound supplement from cached Transfermarkt club manager-history pages.
   It selects only a unique tenure containing the club's first league-fixture
   date and leaves identity, fixture-date and tenure ambiguities as gaps.
   Transfermarkt is credited as the factual source; cached page artwork is not
   redistributed.

   Reconciled opening players must be projected before fixed-capacity carrier
   allocation. `materialise_opening_squad_preallocation_v1.py` binds the exact
   intake, lineup, reconciliation and profiled-additions hashes, then orders
   the sourced XI before the remaining August squad. The package builder
   consumes this projection with `--opening-squad-preallocation`; it does not
   silently truncate a sourced starter. Use
   `opening_evidence_coverage_matrix_v1.py` to produce one consolidated,
   hash-validating coverage matrix across cached season output roots.

   ```bash
   python3 scripts/opening_evidence_coverage_matrix_v1.py \
     --root .local/transfermarkt-opening-plans-v1 \
     --root .local/transfermarkt-opening-plans-expanded-v3 \
     --output .local/transfermarkt-opening-plans-v1/coverage-matrix.json
   ```

   Before collecting those reports, the offline batch planner derives each
   season's Transfermarkt competition map from the FootballSquads selectors.
   Its reviewed static registry covers every catalogue alias currently present
   from 2000/01 through 2025/26. It reports unsupported competitions in
   `plan.json`, excludes them from the strict executable lane, and never fetches
   source pages itself. The generated command remains inert until run explicitly.

   ```bash
   python3 scripts/plan_transfermarkt_opening_lineups_batch_v1.py \
     --seasons-root seasons \
     --output-root .local/transfermarkt-opening-plans-v1
   ```

   Final historical builds must plan from immutable revisions rather than the
   older checked-in intake aliases. The current-revision lane verifies both
   intake and allocation hashes and selects the fixed foreign allocation plus
   all English mode-0 clubs:

   ```bash
   python3 scripts/plan_transfermarkt_opening_lineups_batch_v1.py \
     --historical-current-root .local/season-historical-squad-backfill-v1 \
     --output-root .local/transfermarkt-opening-plans-current-v1
   ```

   A player profile that omits a fact may be supplemented only through an
   explicit source override. `--profile-source-overrides` currently supports
   immutable Wikipedia `oldid` revisions and records the override manifest and
   cached page hashes. The 2001/02 Dean Holness position correction credits
   Wikipedia revision 1355093614 (which in turn cites Soccerbase); it is not an
   inferred position.

4. `season_source_package_builder_v1.py` is the generic mechanical bridge from
   the raw intake toward a package. It consumes the canonical fixed-country
   carrier allocation when present, retains immutable template club/player
   IDs, assigns source-order squads up to each carrier's capacity, applies
   available player facts, and gives mapped source rows deterministic
   `person-source-<row-sha256>` identities. Ratings remain untouched.

   The builder always emits a canonical blocker audit. A structurally valid
   draft may be written for inspection, but `--output-package` fails closed
   while manager, kit, opening, calendar, rating, allocation or identity gaps
   remain. The draft is not a playable/release claim.

   ```bash
   python3 scripts/season_source_package_builder_v1.py \
     --template-package seasons/2015-16/season-package.json \
     --source-intake <season-directory>/source-intake.json \
     --registry <season-directory>/fixed-carrier-registry.json \
     --carrier-allocation <local-build-root>/carrier-allocation.json \
     --output-audit <local-build-root>/source-package-audit.json \
     --output-draft-package <local-build-root>/season-package-draft.json
   ```

   A fully resolved source normaliser and evidence-backed editorial
   reconciliation ultimately create

`data/preferred-season-releases-v1.json` is the single authoritative catalogue
